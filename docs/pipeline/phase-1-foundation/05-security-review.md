## 2. Findings, ranked

Severity scale: **High** = must be resolved in the named artefact before it is accepted; **Medium** = must be resolved in LLD/build, verified at the next gate; **Low** = should be resolved; note if deferred.

### F-1 — HIGH — ADR-0010 is internally inconsistent about `sys.*` vs the `commands ⊆ capabilities` invariant, and the `sys.*` namespace has no admission rule
- **Where:** ADR-0010 Decision points 1, 2, 4, 5; HLD §3.3, §4.4.
- **What:** Point 1: "A capability may be in `capabilities[]` and absent from `commands[]`; the reverse is a profile validation error." Point 5: every Phase 1 profile advertises `commands = [sys.identify, sys.ping]`. No Phase 1 profile in HLD §3.3 lists a `sys.*` entry in `capabilities[]`. Read literally, every Phase 1 profile fails validation, and point 2's first rule ("class not in `capabilities[]` → `capability_not_advertised`") rejects the commissioning guided test. The LLD would have to invent an exemption. Second, point 4 says `sys.*` commands "are not subject to interlock or safety-envelope checks (they actuate nothing)" — the exemption is justified by a property (non-actuation) that nothing enforces at admission time. The reserved `sys.backfill` shows the set is expected to grow.
- **Rule:** ADR-0002 ("capability absent/incompatible is a first-class outcome"), device-control-model §5 (edge validates against profile + envelope + interlocks); security-architecture §4.2 (controller rejects anything outside the envelope "regardless of who asked").
- **Fix shape (ADR-0010 amendment, before the owner accepts it under brief Q-10; LLD adopts the amended reading):** either (a) declare `sys.*` actions to hang off `control.compute` in the profile (`commands[]` entry `{class: control.compute, actions: [sys.identify, sys.ping]}`, or an equivalent explicit rule that `sys.*` satisfies the subset invariant via `control.compute`), or (b) exempt the `sys.*` namespace from the subset invariant and validate it against a **closed, enumerated** list in `docs/iot/schema/v1/` (like `reason_code`). In both cases add: *a `sys.*` command is admitted to the namespace only if it drives no output (relay, PWM, 0–10 V, LED, pump) — this is the property that justifies skipping interlock/envelope checks; a command that touches any output is a crop-control class, never `sys.*`; adding a `sys.*` member requires amending this ADR.* The edge must reject any `sys.*` action not in the enumerated list with `action_not_supported`.

### F-2 — MEDIUM — Sim overlay trust-anchor swap and ACL-volume persistence are unspecified; "harness principal never in prod" holds for the compose file but not yet for persisted broker state
- **Where:** HLD §7.2 (harness "exists only in the sim overlay's ACL file"), §8.1 (`acl_file` from the `mosquitto-acl` volume, `cafile` from secrets), §8.2 (overlay "init step for the ephemeral sim PKI + harness ACL entries"; the 72 h soak runs "on the deploy host or dev box"); ADR-0011 point 2.
- **What:** For the overlay's virtual room controller and harness client to connect, the broker must trust the ephemeral sim CA — i.e. the overlay replaces (or appends to) the prod `broker_ca_cert`. And if the overlay's init step writes harness ACL entries into the same persistent `mosquitto-acl` volume the backend materialises into, those entries survive overlay teardown on the deploy host. The harness cert would no longer validate once the facility CA is restored, so the residual entry is inert — but "cannot be present in the prod compose" is then true of the file and false of the running broker's config.
- **Rule:** security-architecture §3 (per-device ACLs; OT segment no inbound exposure), §7; ADR-0011 consequence "deliberately inconvenient so the exception does not become the path".
- **Fix shape (LLD + build):** (1) the overlay's broker trust is the sim CA **only** — it replaces, never appends to, `broker_ca_cert`, so no facility-CA principal can connect while the overlay is up and vice versa; (2) harness ACL entries live in an overlay-only ACL file (a second mounted file, or the backend's materialiser regenerates the entire ACL file from the registry on every start and drops anything not derived from it); (3) `docs/ops/restore-drill.md` (or a sibling `sim-on-host` note) states that after any overlay run on the facility host the broker is restarted with the prod secrets and the ACL file is re-materialised; (4) the e2e asserts that a sim-CA certificate is refused by the prod-configured broker.

### F-3 — MEDIUM — Backup bundle scope includes `sessions` and `totp_secrets`; `session_key` handling in the clean-stack restore drill is undefined
- **Where:** HLD §5 Identity row, §5.1 ("every relational table above, org-scoped"), §7.3 (`session_key`: session signing + TOTP-secret encryption; `backup_key` separate), §7.4 ("`backup_key` handling in the drill").
- **What:** `sessions` rows are live bearer identifiers and must not be exported. `totp_secrets` are encrypted under `session_key`, which is not in the bundle (correct) and is not mentioned in the drill: a clean stack with a freshly generated `session_key` restores `users` (argon2id, fine) but cannot decrypt any TOTP secret — every account is locked out of the mandatory second factor, and the drill's "audit intact, counts equal manifest" would still pass.
- **Rule:** security-architecture §1 (backup exposure), §5 (audit), §7 (secrets); locked acceptance item "export/restore into a clean system".
- **Fix shape (LLD + runbook):** exclude `sessions` (and any other ephemeral/bearer table) from the bundle and declare it in `absent_entity_types`-style manifest metadata; state in `docs/ops/restore-drill.md` that the operator's secret set carried to the clean stack includes `session_key` (or split a dedicated `totp_key` from `session_key`, F-12, and carry that); the `export-restore` e2e must log in with TOTP after restore, not just count rows.

### F-4 — MEDIUM — `.gitignore` does not cover `.secrets/`; the HLD asserts it does
- **Where:** HLD §7.3 "Compose secrets files under `.secrets/` (gitignored)"; repo `.gitignore` (contains `.env`, `*.env`, `!*.env.example`, no `.secrets`); prod compose skeleton already references `./.secrets/db_password.txt`.
- **Rule:** security-architecture §1 ("Never in repo"), §7 ("Repo: zero secrets").
- **Fix shape (build-deploy-engineer, same change that uncomments the compose services, before any `.secrets/` file exists):** add `.secrets/` and `*.pem`/`*.key` patterns under `.secrets/` to `.gitignore`; the required `secrets-scan` CI job is the backstop, not the control. Also confirm `ops/pki/` contains scripts only and gitignores its output directory.

### F-5 — LOW (safety, non-actuating) — 28 °C mirror comparator `≥` does not match the source's "exceeds" (`>`)
- **Where:** HLD §6 "Solution temperature hard inhibit | ≥ 28 °C"; brief §5.1 same.
- **Source:** `safety-rules.json irrigation_fertigation.solution_temperature_c.action`: "MV-01 … inhibited if solution temperature **exceeds** 28C"; contracts `safety/interlocks.md`: "Solution over-temperature | **> 28 °C**".
- **Why it matters even though it is conservative:** FR-ALR-06 / brief §0 require rules to be copied verbatim; a mirror that raises at exactly 28.0 °C while the hardware has not inhibited would show "What the hardware has done" for something the hardware has not done. Precision matters more for a mirror than for a band.
- **Fix shape (LLD seed):** comparator `>` on the 28 °C rule (and `> 26` for the operating-max OPERATIONAL rule, consistent with "above 26C" in the note), with the comparator recorded alongside `source_citation`.

### F-6 — LOW — Make `enabled` explicitly non-editable for SAFETY rules
- **Where:** HLD §5 `alert_rules.enabled`, `editable`; D-7 "SAFETY rows never editable anywhere"; §6 enrichment band `enabled: false`.
- **Fix shape (LLD):** the `PATCH /alert-rules/{id}` handler and the repository refuse any change to `enabled`, threshold, comparator, `duration_s`, severity or scope on a rule with `severity = SAFETY` or `is_interlock_mirror = true`; a unit test asserts it; the seed asserts that every SAFETY rule is seeded `enabled: true`.

### F-7 — MEDIUM (alert semantics R2+ inherits) — SAFETY mirror behaviour when the mirrored channel goes STALE/OFFLINE mid-alert is undefined
- **Where:** HLD §6 ("clears after the condition is absent for the clear window with hysteresis"; SAFETY evaluates on `good`/`suspect` only), §4.2 health machine.
- **What:** If the safety-NDIR (or `TE-02`, or a leak puck) stops reporting while a SAFETY alert is raised, "condition absent" could be read as "no breaching sample seen", auto-resolving a SAFETY alert on silence. Conversely a SAFETY alert should probably not *raise* from a single `suspect` sample on a channel that is also flagged `clock_anomaly` — the HLD's `duration_s = 0` plus `suspect` admission is the right conservative default for raise, but resolve needs the opposite bias.
- **Rule:** FR-ALR-03; security-architecture §4.4; contracts `interlocks.md` assertion 3 ("inhibited until an operator explicitly clears it").
- **Fix shape (LLD):** a SAFETY / interlock-mirror alert never auto-resolves on the absence of data; it resolves only on a fresh `good`/`suspect` sample that is in-band (or, for booleans, un-tripped) for the clear window, or by operator resolve when such a sample exists; a STALE/OFFLINE mirrored channel while a SAFETY alert is raised is surfaced in the alert ("monitor channel silent since …"). Named unit test on the state machine.

### F-8 — LOW (physical safety, bench) — Carry two electronics-note conditions into the HLD/firmware brief verbatim
- **Where:** HLD §4.4, §13, §14; electronics note "Safety-rules cross-check" and identify conditions (1).
- **Fix shape (LLD / firmware-engineer brief):** (i) "No Phase 1 bench or HIL rig powers a rack-controller board with a relay module, solenoid, fan driver or LED driver connected; a Phase 1 bench is a 3.3 V/5 V/24 V logic rig with no loads." (ii) "The identify status-LED GPIO is chosen so that it is neither an ESP32 strapping/boot-glitch pin nor shared with any relay, PWM, or 0–10 V line; the board config records which pin and why." The R2 gate in §13 should read as a **hard** gate: no firmware version that maps a relay pin is flashed onto a board with relays fitted until the polarity/boot/brown-out bench check for that board revision has passed and is recorded (contracts `valve-fail-states.md` "Consequence for procurement and commissioning").

### F-9 — LOW — `simctl` HTTP control surface must be unreachable from outside the overlay
- **Where:** HLD §2 table, §4.7, §14 (LLD decides "local CLI/HTTP").
- **Fix shape (LLD/build):** `simctl` HTTP binds to the overlay's internal network (or loopback inside the `virtual-room` container), is never published on a host port, carries no auth-bypass to the backend, and the `boundary-check`/compose lint asserts the prod compose file has no `sim` service and no `simctl` port.

### F-10 — LOW — ADR-0011 / §8.1 should state the remaining TLS parameters
- **Where:** ADR-0011 Decision; HLD §8.1, §7.3.
- **Fix shape (ADR-0011 note or LLD):** broker server certificate issued by the same facility CA (or state the alternative); every client verifies the broker certificate against `broker_ca_cert` with hostname/SAN check and no insecure-skip-verify anywhere (including `sim/`); listener `allow_anonymous false` stated explicitly; minimum TLS 1.2 with ECDHE suites (TLS 1.3 preferred); certificate validity period and the `credential_expiring` DEGRADED threshold recorded as labelled design parameters; the offline CA key stored passphrase-encrypted on removable media with the passphrase separate, per the ops runbook; `ops/pki/` in-repo contains scripts and a README only.

### F-11 — LOW — Room-controller publish prefix includes its own room's `cmd` leaf
- **Where:** HLD §7.2 principals table (`rmc-NN` publish `…/<room>/#`).
- **What:** A compromised room controller could publish `cmd` (and spoof `ack`) for nodes it already owns on the bus — no privilege gain in Phase 1, but in R2 it lets the field client originate commands over MQTT that the backend's allow-list and audit never see.
- **Fix shape (LLD ACL):** add a deny for `…/<room>/+/+/cmd` publish on the room-controller principal (Mosquitto ACL order allows it), so `cmd` originates only from the backend principal; the org-scoping Mosquitto test gains that case.

### F-12 — LOW — Key separation: one `session_key` for session signing and TOTP-secret encryption
- **Where:** HLD §5 Identity row, §7.3.
- **Fix shape (LLD):** sessions are server-side opaque ids and need no signing key; if a signing key is kept, split `totp_key` (data-at-rest encryption, must travel with backups, F-3) from `session_key` (ephemeral, rotation logs everyone out). Different rotation semantics justify different keys.

### F-13 — LOW — Supply-chain obligations from the ADR-0009 review are not carried by name; no Go-side equivalent; container/image pins incomplete
- **Where:** HLD §8.3; `docs/pipeline/frontend-framework-adr/05-security-review.md` §2 items 1–2; workflow `go-version: stable`, `espressif/idf:latest`, `eclipse-mosquitto:2`.
- **Fix shape (LLD/build):** frontend — committed `package-lock.json`, `npm ci` only, `ignore-scripts` (or an allow-listed audit of install scripts), dependency bumps by reviewed PR only, re-check the `vite-plugin-pwa`/`serialize-javascript` transitive advisory at scaffold time; backend and sim — `go.mod`/`go.sum` committed, CI builds with `-mod=readonly`, `govulncheck` in the Go jobs, pinned Go toolchain version; images — digest-pin `eclipse-mosquitto` and `timescaledb` in the prod compose and the ESP-IDF container in CI. None of this is safety-critical in Phase 1; it becomes so the moment R2 puts an actuating command through the same binaries.

### F-14 — LOW — Say plainly that `rack-link/0` is unauthenticated and integrity-unprotected, and bound it
- **Where:** HLD §3.2.
- **Fix shape (HLD note at docs-writer time, or LLD `rack-link-0.md`):** "`rack-link/0` has no authentication, no integrity protection and no replay protection; the virtual room controller trusts whatever is on the serial adapter. This is acceptable only because Phase 1 has no actuation and the adapter is a bench USB-serial link; the R2 Modbus map (contracts v0.3.0) and the two-party commissioning fingerprint attestation are the items that must close before a bus-attached device is trusted for anything that moves." The R2 attestation item already in §3.2/§14 stays.

### F-15 — MEDIUM (existing design, recorded here; R2 trigger) — CI deploy step opens an inbound SSH path from GitHub Actions into the facility host that also runs the broker
- **Where:** HLD §8.3 `deploy` row (SSH to the facility host, `git pull`, `docker compose … up -d`, `backend migrate`; deploy key as a GitHub secret). Pre-existing in the workflow's placeholder and the release plan; the HLD makes it concrete.
- **Rule:** security-architecture §3 ("OT segment (controllers, sensors, broker) has no inbound exposure"; cloud-to-edge outbound-only where possible); ADR-0001 (backend outage is a non-event — a compromised deploy is not).
- **Why not blocking now:** Phase 1 has no actuation and no real device; a compromised runner can at most disturb telemetry on a virtual facility.
- **Fix shape (github-ops-agent / build-deploy-engineer):** prefer a pull-based deploy (host polls or a self-hosted runner on the facility LAN with outbound-only connectivity) over an inbound SSH hole; if SSH stays for Phase 1: dedicated deploy user with a forced command restricted to the compose/migrate script, key scoped to a single environment with required reviewers on `main`, host allow-list on the SSH daemon, and the deploy job pinned to reviewed actions. **Record as an R2 hard condition:** before the first actuating release, no CI-originated path may reach the host that runs the broker without a human approval gate.
