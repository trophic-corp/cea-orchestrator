# 0009. Vue 3 as the operator console frontend framework

**Status:** proposed
**Date:** 2026-09-08
**Pipeline artifact:** docs/pipeline/frontend-framework-adr/

> **Why `proposed` and not `accepted`.** Mirrors ADR-0006's convention: the decision itself
> is settled (see below); it is recorded as `proposed` only because it hasn't gone through a
> merged PR yet. `docs-writer` flips it to `accepted` once that PR merges — never before.
> Unlike ADR-0006, this ADR is not waiting on OQ-3 for any reason: nothing about
> room-controller compute platform touches a console framework choice (see Consequences).

## Context

`frontend/` exists only as an empty directory (`.gitkeep`) with no framework choice recorded
anywhere. No prior ADR covers frontend territory: ADR-0006 (Go as backend language) is the
nearest analog in spirit — a language/framework choice with alternatives weighed — but
scopes `backend/` only; ADR-0008 (monorepo with named split triggers) governs *boundary
discipline* between `frontend/`, `backend/`, and `firmware/` but is silent on which frontend
framework lives inside that boundary. This is a genuine greenfield decision, not an
application of an existing one.

The console's shape is fixed by prior decisions and documents, and constrains the framework
choice rather than being decided by it:

- **App genre.** Per `docs/roadmap/release-plan.md`, Release 1 is Home / Grow drill-down /
  Devices / Alerts / Settings; Release 2/3 add control panels, a recipe editor, and a batch
  board. This is an admin/dashboard/forms-shaped application, not a marketing site or a
  content-heavy public surface.
- **Capability-based device model (ADR-0002).** Device capability classes
  (`device-control-model.md` §3 — `light.dim {min,max}`, `irrigation.flood
  {depth_mm,dwell_min,cycle}`, `valve.control {failsafe_state}`, `co2.enrich
  {target,alarm}`, `dosing.fertigation {profile}`) are small, flat-to-shallow parameter
  sets — exactly the shape JSON-Schema-driven form rendering is built for. The console must
  render controls that appear only when a capability exists, record "not applied — lacks
  capability" for recipe parameters a zone doesn't support, and tolerate capability
  classes/schema versions it doesn't recognize without crashing (ADR-0002 forward-
  compatibility requirement). This is an application-logic and rendering-tolerance
  responsibility built on top of whatever schema-driven form layer is chosen, not something
  any framework provides automatically — noted here so it isn't mistaken for solved by the
  framework pick alone.
- **Edge authority (ADR-0001).** The console must represent edge-authority honestly (stale
  badges, "edge-autonomous" banners) and must not be mistaken for the safety-envelope
  enforcement point: any client-side validation of capability/safety-envelope bounds
  (e.g., encoding `safety-rules.json` bounds as JSON Schema `minimum`/`maximum`/`enum` for a
  recipe-editor confirmation dialog, IA journey J4) is a UX convenience for fast rejection
  only — the room controller remains the enforcing authority per ADR-0001 point 3 and
  device-control-model §5, regardless of framework.
- **MQTT/Timescale/Postgres backbone (ADR-0004).** ADR-0004 names the room controller as the
  sole MQTT client on the field-bus side and backend/cloud readers as separate MQTT clients
  with their own ACLs. It does not name the console as an MQTT client at all — "no service
  ever talks to a rack controller or I/O node directly" and the console is not a service in
  that sense either. The console's access path is the backend's HTTP/OpenAPI surface only.
- **OpenAPI as the contract of record (ADR-0006, ADR-0008 rule 1).** Shared types between
  `backend/` and `frontend/` must be generated from the OpenAPI spec, never shared by file
  path.
- **Monorepo boundary discipline (ADR-0008).** `frontend/` must keep its own build and
  dependency manifest with an independently runnable CI job, and must not import across
  `backend/`/`firmware/` directory lines.
- **IA gate (`docs/ux/information-architecture.md` §6).** Hi-fi visual/interaction design is
  deferred until IA + journeys J1–J7 are reviewed and Release 1 scope is frozen. That gate
  governs screens and Figma work, not the framework/tooling decision underneath — this ADR
  does not anticipate or prejudge it.

Reactivity load is modest by design: ADR-0006's own throughput finding puts device message
volume at single-digit messages/second, and the console reflects that same low-frequency
telemetry per tier/zone rather than anything approaching real-time high-frequency streams.

## Decision

**The operator console is built with Vue 3 (Composition API, `<script setup>`) + TypeScript
+ Vite.**

Supporting library set:

- **Data layer:** `@tanstack/vue-query` for caching/invalidation, wrapping a client
  generated by openapi-typescript (spec → TS types) + openapi-fetch (typed fetch client) —
  the framework-agnostic realization of the OpenAPI-as-contract requirement (ADR-0006,
  ADR-0008 rule 1). No shared types by file path.
- **Charts:** vue-echarts + uPlot.
- **Schema-driven forms:** FormKit or `vue-json-schema-form`, for device commissioning and
  the recipe editor — rendering capability-aware, envelope-annotated forms per ADR-0002
  above. This capability is a property of the JSON-Schema-driven form *pattern* generally
  (equally available in the React ecosystem via react-jsonschema-form/uniforms), not a
  Vue-specific differentiator — it is satisfied by the chosen stack, not a reason the stack
  was chosen.
- **Routing/state:** Vue Router; Pinia only if state is needed beyond the query cache.
- **Utilities:** VueUse, including online/offline detection (console must tolerate
  disconnection gracefully, consistent with ADR-0001's local-first posture).
- **Delivery:** static bundle served by the Go backend — no Node runtime on the facility
  host. PWA via `vite-plugin-pwa`.

**Explicit PWA caching boundary, per security review (`05-security-review.md`): the service
worker may cache the app shell (static assets) only. All API responses — telemetry, alarm
state, device/command status — are fetched network-first/network-only, never
cache-first/stale-while-revalidate.** IA principle 4 ("never renders stale state as
current") and ADR-0001's edge-authority honesty requirement both fail if a genuine active
alarm or stale-device state is ever served from a service-worker cache as if fresh. Offline
mode means "the app shell loads and shows an explicit disconnected state," never "the last
cached alarm/telemetry snapshot is shown as current." This binds the PWA config, not just
this ADR's prose — the eventual `vite-plugin-pwa` `workbox` config must implement it.

**Explicit boundary: the console is an HTTP/OpenAPI client of the backend only. It never
opens an MQTT connection of its own, including for "real-time" telemetry.** Live/near-live
updates are backend-mediated — polling via `vue-query`, or a future backend-owned
websocket/SSE relay if polling proves insufficient — never a browser-side MQTT.js client
reaching toward the broker. This keeps ADR-0004's choke point (room controller is the only
path to field devices; backend/cloud readers are the broker's only other clients) intact:
the console does not become a third kind of MQTT client by accident.

## Consequences

**Easier**
- The console's form/dashboard-heavy shape (Home, Grow, Devices, Alerts, Settings, later
  recipe editor and batch board) is served well by Vue's admin/dashboard ecosystem (Element
  Plus, Ant Design Vue, FormKit) — a genre fit, not just adequate coverage.
- Per-tier/per-device telemetry updates independently without `useMemo`/selector discipline
  being load-bearing for correctness as zone count scales — Vue's proxy-based reactivity
  updates only the affected subtree by default. This matters more as a correctness-by-default
  property than a performance one, given the single-digit-msg/s load ADR-0006 already
  established.
- SFC's template/script/style separation reads closer to HTML/CSS/TS than JSX's interleaving
  — lower review cost for a small, bus-factor-1 team, the same owner-fluency/reviewability
  logic ADR-0006 used to decide Go.
- Most frontend code, like the backend, will be agent-authored. SFC's physical separation of
  markup/logic/style is arguably easier for an agent to generate correctly than JSX's
  interleaving; AI-authorship quality is otherwise roughly comparable between Vue and React
  (both well-represented in LLM training data).
- Composition API has been stable since 2020, with no equivalent of Svelte 5's runes rewrite
  on the horizon — lower risk of a forced reactivity-model migration over this system's
  multi-year expected lifetime.

**Harder**
- Ecosystem breadth is narrower than React's in absolute terms (fewer total packages,
  smaller Stack Overflow/tutorial corpus). Accepted: the specific libraries this app needs
  (charts, schema-driven forms, dashboard chrome) are equally mature in Vue, so the
  narrower-in-general ecosystem doesn't bite for this app's actual needs.
- Smaller hiring pool than React, in principle. Accepted for the same bus-factor-1 reasons
  ADR-0006 accepted a smaller Go hiring pool locally — largely theoretical at current team
  size.

**Must now be respected rather than re-derived**
- Any future console work (scaffold, screens, additional libraries) builds on Vue 3 +
  TS + Vite rather than re-litigating the framework choice, unless a documented reason
  supersedes this ADR.
- The eventual `frontend/` scaffold must honor ADR-0008 rule 4 (own build/dependency
  manifest, independently runnable CI) and rule 1 (OpenAPI-generated types only, no
  cross-directory type sharing) — pre-committed here the same way ADR-0006 pre-committed
  Go's CI/compose obligations before the backend was built.
- The console never opens an MQTT connection directly, per the explicit boundary above —
  binding on all future console work, not just the initial build.
- The service worker caches the app shell only; API/telemetry/alarm data is always
  network-first/network-only, per the explicit PWA caching boundary above — binding on the
  eventual `vite-plugin-pwa` config, flagged by `security-safety-reviewer` (05) as a
  pre-code architectural commitment rather than an implementation detail to decide later.
- **This ADR binds the operator console only.** It does not bind:
  - The **B2B portal** (Release 5, a separate application per IA principle 7), which may
    reconsider this framework choice independently if its needs diverge from the operator
    console's — e.g., an SSR/SEO requirement that never applies to an authenticated,
    LAN-served operator tool but plausibly does apply to a public-facing portal.
  - The **room-controller local UI** (OQ-3, closing as a future ADR-0007), which does not
    yet exist and is not decided by this ADR — though it should likely follow the same
    choice for consistency once it exists, absent a reason specific to that surface (e.g.
    a hard constraint from whatever compute platform OQ-3 lands on).
- Building the actual console screens is not authorized by this ADR. It remains gated by
  `docs/ux/information-architecture.md` §6 (IA/journey review, Release 1 scope freeze) and,
  independently, by the roadmap's Phase 1 build pause pending OQ-3/ADR-0007. This ADR records
  the framework only; no scaffold, `docker-compose.prod.yml` edit, or CI job follows from it
  in this `/ship` run.

**Cannot be reversed by OQ-3.** OQ-3 decides room-controller compute platform (Linux SBC,
industrial/panel PC, or facility-host collapse). The operator console is served as a static
bundle by the Go backend on the facility host regardless of that outcome — no OQ-3 result
changes what the console runs on or how it's served. This ADR is therefore not gated on
ADR-0007, the same reasoning ADR-0006 used for Go.

## Alternatives considered

**React + TypeScript + Vite.** Real advantage: broader ecosystem in absolute terms. But the
*specific* libraries this app needs — charts, schema-driven forms, dashboard chrome — are
equally mature in Vue's ecosystem, so that breadth doesn't translate into an advantage for
this app's actual requirements. Schema-driven capability-aware forms specifically are
achievable in both ecosystems (FormKit/vue-json-schema-form vs. react-jsonschema-form/
uniforms) and are not treated here as a differentiator. JSX's markup/logic interleaving is a
real, ongoing readability cost for a small reviewing team, mirroring the SFC-separation
argument above in reverse. Not decisive enough on its own to override the genre-fit and
reviewability case for Vue, but the closest alternative and the one most likely to be
reconsidered if a future need (e.g., the B2B portal, or a hiring change) shifts the balance.

**Svelte + TypeScript + Vite.** Closest to plain HTML/CSS/JS, smallest bundle and runtime —
genuinely appealing on technical merits, and bundle size would matter more if this were
public-internet-served. It is not: the console is served over LAN to an operator on a
facility host, so bundle size and raw popularity are explicitly not deciding factors here.
Rejected primarily on **long-term stability risk**, not technical merit: Svelte's ecosystem
is thinner for this app's actual needs (schema-driven forms, dashboard chrome), and the
Svelte 4→5 runes rewrite is a real precedent for another breaking reactivity-model change
within this system's multi-year expected lifetime — a risk Vue's Composition API (stable
since 2020) does not carry.

**Web Components / Lit.** Not seriously considered. Would forfeit the schema-driven-forms
and dashboard-chrome ecosystem both Vue and React provide, in exchange for a
framework-interop/portability benefit nobody has asked for at this scale.

**Bundle size and raw popularity as deciding criteria.** Explicitly rejected as decision
inputs: the console is served over LAN from the facility host to an operator, not over the
public internet to anonymous visitors, so neither criterion carries the weight it would for
a public-facing app.
