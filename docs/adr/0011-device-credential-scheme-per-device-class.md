# 0011. Device credential scheme, per device class: mTLS with ECC P-256 certificates from an offline facility CA

**Status:** proposed
**Date:** 2026-09-10
**Pipeline artifact:** docs/pipeline/phase-1-foundation/ (`03-domain-brief.md` §1, §6.1; `04-hld.md` §7.2)
**Satisfies:** `docs/security/security-architecture.md` §2 ("per-device PSK acceptable
first-phase compromise documented in an ADR when firmware work starts") and §6.6 of the
Phase 1 PRD (security pass item: "device credential scheme — mTLS or PSK-with-justification
— recorded in a new ADR")

## Context

Security-architecture §2 requires a unique identity per device with an individual
credential, states that a client certificate via mTLS is **preferred**, and allows
per-device PSK as a **first-phase compromise** provided it is documented in an ADR when
firmware work starts. Phase 1 is that firmware work. §3 requires Mosquitto to enforce
per-device topic ACLs; §7 requires credentials on the edge to live in a secure element or
encrypted NVS; §9 rules out operating any PKI "beyond per-device certificates issued at
provisioning (offline CA at commissioning time is acceptable at this scale)".

The argument that would favour PSK is cost on a microcontroller: an mbedTLS session with
client-certificate authentication on a classic ESP32 costs tens of kilobytes of heap and,
with RSA, seconds of handshake (electronics note §3.3). The Phase 1 domain brief (§1)
removed that argument from the decision:

- In the documented build, **rack controllers are Modbus RTU slaves**, not MQTT clients
  (ADR-0004 point 1; trophic-contracts `sensors/instrument-tags.md`). Phase 1 gives them
  `rack-link/0` over UART and **no MQTT, TLS, or broker credential at all**.
- The **only MQTT-client device class in Phase 1 is the room controller**, and it is virtual
  — a Go process (`sim/cmd/virtual-room`) on the facility host or in CI. The real room
  controller is disqualified from ESP32-class hardware by the OQ-3 brief (§2) regardless of
  which option A/C/D closes it: it will run a full TLS stack.
- The two places an MCU might ever hold a broker credential are exceptions: a compile-time
  bench flag for ESP32 bring-up (deleted before R2) and the documented wireless-retrofit
  path for a rack that cannot be cabled (Rack A Spec §07). Electronics §3.3 already states
  that both are feasible with **ECC P-256** certificates and dynamic TLS buffers.

Two facts about the broker also bear on it. Mosquitto configures TLS-PSK (`psk_file`) and
certificate-based TLS on a listener **mutually exclusively**, so a fleet mixing PSK devices
with certificate-authenticated service clients needs two listeners and two ACL identity
mappings. And Mosquitto's `use_identity_as_username` maps a certificate CN straight to the
ACL username, which makes "certificate = identity = ACL principal" a one-line configuration.

The evidence therefore does decide. The credential type is nonetheless recorded **per
device class** as a registry attribute (electronics Q5.3), so that a future class with a
genuine constraint can carry a different scheme without reopening this ADR for the fleet.

## Decision

1. **Every MQTT-client device class authenticates to the broker with mutual TLS using a
   per-device ECC P-256 client certificate.** Certificate `CN = device_id`. Mosquitto runs
   one listener (`8883`) with `require_certificate true` and
   `use_identity_as_username true`; topic ACLs are keyed by that username.
2. **Certificates are issued by an offline facility CA at provisioning** (security §9). The
   CA private key is never on the facility host, never in a container, never a compose
   secret. Issuance is an operator CLI step; the registry records the certificate's
   public-key fingerprint as `credential_fingerprint` and the principal's `acl_prefix`. In
   CI and the sim overlay, an ephemeral CA and certificates are generated by the harness.
3. **`credential_type` is a per-device-class registry attribute.** Phase 1 values:

   | Device class | `credential_type` | ACL prefix |
   |---|---|---|
   | room-controller (`rmc-NN`; virtual in Phase 1) | `mtls-ecc-p256` | `trophic/<org>/<site>/<room>/#` (publishes on behalf of every node it bridges) |
   | rack-controller (`rc-NN`) | `none` — bus node behind the room controller | — |
   | io-node (`io-terrace`, `io-skid`, `io-room`) | `none` — bus node | — |
   | bench-direct ESP32 (bring-up only, never production) | `mtls-ecc-p256` from a **bench CA** the production broker does not trust | `…/<zone>/<device>/#` |

   Backend service principals (ingest) use a service certificate from the same facility CA
   with their own ACL (publish `…/cmd` only in Phase 1; subscribe `trophic/<org>/<site>/#`).
4. **Per-device PSK is not adopted, not even as a first-phase compromise.** The condition
   that would justify it (an MCU that must terminate TLS on the production path) does not
   exist in Phase 1 and is not expected in R2 for the room-controller class.
5. **Rotation and revocation:** re-issue with the same CN and revoke the old serial via a
   CRL file the broker reloads; no re-flash is implied because no Phase 1 MQTT client is
   firmware. On real MCU hardware (bench flag, wireless retrofit), credentials live in
   encrypted NVS / a secure element (security §7) — a requirement on that future firmware,
   not a Phase 1 deliverable.
6. **Identity is not trust.** A certificate gets a device onto the broker inside its ACL
   prefix; it does not claim the device. Lifecycle (UNCLAIMED → CLAIMED → … ) is a registry
   state; an unclaimed device receives no commands at the backend and is refused
   `device_unclaimed` at the edge. A device reappearing with a mismatched hardware
   fingerprint is quarantined (security §2), independent of its certificate being valid.

## Consequences

**Easier**
- One listener, one credential mechanism, one identity → ACL mapping for devices and
  service principals alike. The org-scoping test "a principal cannot publish outside its ACL
  prefix" (AC-ADR-0005a as restated in the brief) is a straightforward Mosquitto test.
- Nothing to remove later: the scheme the preferred architecture wants is the one shipped
  first.
- After a clean-stack restore, devices reconnect with the same certificates; the backend
  re-materialises ACLs from the restored registry (`device_id → acl_prefix`) and identities
  are preserved without re-provisioning.

**Harder**
- An offline CA is an operational artefact to keep safe and to use correctly at every
  commissioning; the restore drill and the ops runbook must cover it. At one facility this
  is a USB key and a checklist, which is what security §9 anticipated.
- The bench-direct exception, if used, needs a second (bench) CA and a broker that trusts
  it only in a bench configuration — deliberately inconvenient so the exception does not
  become the path.
- Certificate expiry becomes a device-health concern (a `DEGRADED{credential_expiring}`
  reason is reserved; not built in Phase 1).

**Must now be respected rather than re-derived**
- The real room controller (ADR-0007, when OQ-3 closes) inherits `mtls-ecc-p256`; its
  platform must hold the key in protected storage appropriate to that platform.
- Any future MCU class that must be an MQTT client on the production path (e.g. a wireless
  retrofit rack controller) uses **ECC P-256 mTLS**, not RSA and not PSK, unless a
  superseding ADR records a measured constraint that makes it infeasible on the chosen
  part.
- The backend's ACL materialisation is a provisioning-time action; the backend is never in
  the broker's authentication or data path.

## Alternatives considered

- **Per-device PSK (TLS-PSK) as the first-phase compromise security §2 allows.** Cheapest
  on an MCU and simple to provision. Rejected because no Phase 1 MQTT client is an MCU;
  because Mosquitto's PSK and certificate modes are per-listener exclusive, so PSK devices
  would force a second listener and a parallel identity mapping that the service principals
  do not use; because PSK rotation means re-provisioning both ends with a new shared secret
  rather than re-issuing against a stable CA; and because the compromise would have to be
  unwound in R2 anyway.
- **Username/password over TLS (server-auth only) per device.** Simplest to script, but it
  is a bearer secret in transit at every connect, gives the broker no cryptographic binding
  between identity and key, and security §2 does not list it as acceptable. Rejected.
- **mTLS with RSA-2048 certificates.** Equivalent on Linux, but the electronics note is
  explicit that RSA client authentication on ESP32-class hardware takes seconds and a large
  stack; choosing ECC P-256 fleet-wide now means the bench flag and the wireless-retrofit
  exception need no second scheme. Rejected in favour of ECC.
- **Mixed scheme — mTLS for Linux-class devices, PSK for MCU-class devices, decided
  fleet-wide now.** Reasonable in the abstract and the reason `credential_type` is a
  per-class attribute; rejected as a Phase 1 *decision* because no MCU-class MQTT client
  exists to decide for, and electronics §3.3 shows ECC mTLS is feasible for the two
  exceptions if they ever ship.
- **An online CA / enrolment service inside the backend (ACME-style, EST).** Would make
  provisioning a web endpoint on the facility host and put the CA key in a container.
  Security §9 forbids operating that PKI; at 14 bus nodes and one room controller the
  offline CA is the proportionate choice. Revisit at productization (ADR-0005 trigger).
